SLIDE 02 The Problem

Why does CPU scheduling fail?

Starvation

Low-priority processes wait indefinitely when high-priority processes keep arriving. They may never execute.

Static Priorities

Fixed priorities ignore how long a process has been waiting. No fairness mechanism exists in classic priority schedulers.

Poor Response Time

Interactive processes suffer when blocked behind long batch jobs with no urgency awareness or adaptive escalation.

Problem Statement
"Design a CPU scheduler that dynamically adjusts process priorities to reduce starvation and improve response time."

SLIDE 05 Core Innovation

Dynamic Priority Aging

STEP 1 Every tick, inspect all READY waiting processes
STEP 2 If waiting_time % 5 == 0, boost priority by +1
STEP 3 Cap boost at +5 above original. Flag if wait > 20 units.
new_priority = original_priority - floor(waiting_time / 5) effective = max(new_priority, original_priority - 5) if waiting_time > 20: flag_starvation(process)
Aging Interval: 5 units
Max Boost: +5 levels
Starvation Threshold: >20 units
SLIDE 06 Implementation

Four scheduling modes

FCFS
Non-preemptive

Executes processes in arrival order. Simple, fair for equal workloads.

Limitation: Convoy effect — one long job delays all others.
Round Robin
Preemptive

Time-slice quantum (configurable). Each process gets equal CPU turns.

Limitation: Ignores urgency — high-priority jobs wait equally.
Priority (Static)
Non-preemptive

Runs highest-priority process first. Fast for known workloads.

Limitation: Low-priority processes starve indefinitely.
Dynamic Priority (Aging)
Dynamic

Priority adjusts in real time based on waiting time. Eliminates starvation.

Strength: Guaranteed execution for every process.

Static Priority vs Dynamic Aging

Dynamic Priority (With Aging)

Average Waiting Time: 9.40 units

Dynamic Aging ensured fair progressive priority escalations, bounding maximum latency and maintaining balanced queue turnaround.
On starvation-prone workloads, Dynamic Priority eliminates starvation entirely — static scheduling cannot guarantee this.
